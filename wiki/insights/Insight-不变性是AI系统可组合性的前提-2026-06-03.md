# 不变性是 AI 系统可组合性的前提

## 碰撞来源

三篇风马牛不相及的文章：多 Agent 团队协作的角色分工策略、Prompt Caching 的 KV Cache 机制、以及个人知识库的增量入库工作流。表面上分别属于工程协作、成本优化和知识管理三个领域，但它们共享同一个底层结构。

## 核心洞见

这三个系统都在解同一个问题：**如何在变化中识别并保护不变的部分，从而让差量计算成为可能。**

- Prompt Caching 的前提是"前缀不变"——系统提示固定，才能让 KV Cache 在跨请求间复用；一旦在系统提示中注入时间戳，缓存即失效
- Agent Teams 的前提是"角色不变"——Team Lead 永远是 Opus，核心成员永远是 Sonnet；角色定义的稳定性是并行协作的前提，不是可选的
- 知识库增量入库的前提是"账本不变"——幂等检查依赖 LEDGER 准确记录已处理状态；如果账本被污染，增量处理退化为全量重跑

三者的"不变量"各不相同（Token 前缀、角色定义、入库账本），但它们保护不变量的目的一致：**让差量可以被独立计算，从而实现组合而非重复**。

## 结构抽象

可以将这个模式形式化为：

```
系统效率 = 不变基座的稳定性 × 差量部分的最小化
```

当"不变基座"被破坏时，系统退化为全量计算：
- Prompt Caching 失效 → 每次请求重新计算全量 Token
- Agent 角色漂移 → 协作失去可预测性，无法并行
- 幂等账本失效 → 每次入库重扫全部 raw 文件

## 延伸：不变性的维护成本

三个系统也共享另一个特点：**维护不变量本身有成本，且成本随时间递增。**

系统提示越来越长，缓存命中率不降反升，但注入动态内容的诱惑也越来越大。Agent 角色随任务复杂度升级，原有角色定义可能不再适用。知识库账本需要随文件迁移、重命名而同步更新。

不变量的维护若被忽视，最终会导致系统在某个看不见的临界点突然退化。这是 AI 系统中"技术债"的一种特殊形式：不是代码腐化，而是**结构不变性的悄然腐化**。

## 实践含义

设计 AI 系统时，应当首先识别哪些部分需要被设计为不变量，然后**主动为这些不变量设置守护机制**——而不是依赖开发者的自律。Prompt Caching 通过架构强制（前缀机制），Agent Teams 通过配置文件（CLAUDE.md 声明），知识库通过幂等账本（LEDGER）——这三种守护方式对应了不同的约束强度，但目的相同。
