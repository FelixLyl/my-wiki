# 代码知识的三向流动：知识沉淀双轨与图谱查询的结构融合

## 碰撞起点

[[知识沉淀双轨机制]] 将代码经验分为"私有轨"（本地调试笔记）和"共享轨"（团队最佳实践）。[[Graphify-代码知识图谱]] 提供代码结构的图谱底座，将函数调用、模块依赖、论文概念三类节点统一表达。[[代码简化工具]] 则专注单一维度——在不改变功能的前提下提升代码可读性。

三者乍看分属"经验存储"、"结构理解"、"代码转化"三个独立问题，但它们共同指向一个更深层的问题：**代码知识到底沿哪些路径流动，在什么节点应该被拦截、提炼和沉淀？**

## 洞见：代码知识存在三个流向，现有工具各守一关但缺乏协同

代码知识的流动可以拆解为三个方向：

1. **纵向沉淀**（时间维度）：代码经验从"当下发现"变为"未来可调用的资产"。这是双轨机制的关注点。
2. **横向结构化**（空间维度）：代码模块之间的依赖和调用关系从"隐式存在"变为"可查询的图谱"。这是 Graphify 的关注点。
3. **密度简化**（质量维度）：代码从"功能正确"变为"认知负担低"。这是 Code Simplifier 的关注点。

当前的问题是：**三个流向之间没有桥梁**。

- Graphify 能告诉你某个函数被哪些模块调用，但不知道这个函数是否在某次调试中发现了一个私有坑（双轨机制的私有轨内容）。
- Code Simplifier 能简化代码，但简化后的洞察（"这类嵌套结构可以用 switch 替换"）并没有自动沉淀到共享轨。
- 双轨机制告诉你"任务结束时评估经验"，但没有机制让 AI 在简化代码时顺手标注哪些图谱节点的理解密度已经改变。

## 结构融合的可能路径

一个完整的代码知识系统，理论上需要让三个流向互相感知：

**简化操作 → 触发图谱更新**：当 Code Simplifier 将嵌套三元运算改为 switch 后，对应的 Graphify 节点应标记"可读性已提升"，并将简化模式（"嵌套三元 → switch"）作为模式节点沉淀进图谱。

**图谱路径 → 触发双轨判断**：当 Graphify 发现某个函数节点的入链极多（高耦合），这一结构特征应自动触发双轨机制的共享轨写入——"高耦合节点的依赖风险"是值得团队共享的架构知识，而不只是私人笔记。

**双轨经验 → 反哺简化策略**：私有轨记录的"这个项目中 async/await 比 Promise 链更易维护"，应能作为 Code Simplifier 的上下文约束——把私有经验转化为针对该项目的简化偏好。

## 底层模式命名：认知密度的三层捕获

这三个流向实际上是在捕获同一对象（代码）的不同维度认知密度：

- 双轨机制捕获的是**行为层密度**（什么值得重复做，什么要避免）
- Graphify 捕获的是**结构层密度**（节点间的关系拓扑有多复杂）
- Code Simplifier 捕获的是**表达层密度**（同等语义下的最小认知负担）

现有工具割裂地处理三层，但代码质量的提升需要三层联动。**一个真正的代码知识系统应当让表达层的简化能触达结构层的图谱，结构层的图谱又能触达行为层的经验沉淀。**

## 实践建议

在现有工具拼合的场景下，可以手工建立连接点：
- Code Simplifier 执行后，将简化类型标注写入 CLAUDE.md 的项目经验章节（双轨机制的共享轨）
- Graphify 分析高耦合节点后，将结果导出为 Obsidian 节点并打上"高耦合"标签，进入双轨机制的知识池
- 双轨机制的私有轨笔记在转为共享轨时，优先补充 Graphify 图谱中尚无描述的节点

这是在工具未打通之前，依赖人工维持三层流动的最低成本方案。
