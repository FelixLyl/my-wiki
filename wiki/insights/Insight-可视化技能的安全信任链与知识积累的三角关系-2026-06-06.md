# 可视化技能、安全信任链与知识积累的三角关系

## 三篇文章的表面内容

- [[Markdown查看器技能]]：一套 15 个 AI Agent 图表生成 Skills，覆盖 7 种渲染引擎，让 Agent 直接在 Markdown 中输出可视化内容
- [[OpenClaw-Agent安全体系]]：高权限 Agent 的安全防线，核心矛盾是"Agent 自主执行"与"人类审批"之间的张力
- [[Andrej-Karpathy]]：将 LLM 定位为 wiki 维护者，强调通过持续约束产生可积累产物

## 隐藏关联：Skill 是知识体系中的"最小信任单元"

三篇文章的共同底层问题是：**在自主系统中，什么东西可以被信任，信任从哪里来？**

Karpathy 的答案是：信任来自于"持续约束+可验证积累"——LLM 编写的 wiki 内容通过时间复利建立信度，而非单次生成的质量保证。

OpenClaw 安全体系的答案是：信任来自于"供应链审查+运行时护栏"——在 Skill 进入系统之前用 skill-vetter 扫描，安装后用 SecureClaw 巡检，运行时用 ops-guardrails 拦截。

markdown-viewer/skills 则暴露了一个被忽视的问题：**可视化能力本身也是 Skill，同样需要经过信任链**。一套 15 个 Skills、7 种渲染引擎的图表库，如果绕过安全审查直接安装，每一个代码围栏都是潜在的执行路径。PlantUML、Graphviz 的 dot 语言、Vega 的 JSON Schema——每一层都可能藏有恶意脚本触发点。

## 关键洞见：可视化 Skill 是安全信任链中最容易被忽视的环节

典型的安全威胁模型关注"写文件""发网络请求""执行 shell"这三类高危操作。但图表生成 Skill 通常被归类为"纯渲染/展示"，其实不然：

- PlantUML 需要本地 Java 运行时或远程渲染服务，后者存在数据外泄风险
- Vega 的 `transform` 字段支持 JavaScript 表达式，可以在渲染时执行任意代码
- HTML/CSS 直出模式（architecture/infocard）可以内嵌 `<script>` 标签

这意味着，**可视化能力与执行能力之间的边界比直觉更薄**。

## Karpathy 的约束论在安全语境下的再解读

Karpathy 说 LLM 的价值在于"通过持续约束产生可积累的产物"。在安全语境下，这句话有第二重含义：

一个知识库的**可信度**同样需要持续约束来积累。wiki 文章的 maturity 生命周期（stub → draft → reviewed → authoritative）本质上就是信任链的显性化——每次 review 是一次审计，每次做梦机制的灵感碰撞是一次交叉验证。

如果说 OpenClaw 安全体系在运行时对每个 Skill 建立信任，那么 wiki 的 maturity 机制就是在知识层面对每个"知识断言"建立信任。**两者都在解决同一个问题：如何在自主系统中，让信任的积累速度快于风险的增长速度。**

## 可操作推论

1. 安装图表/可视化类 Skill 时，应与代码执行类 Skill 同等对待，过 skill-vetter 扫描
2. 优先选择纯文本渲染路径（Mermaid/PlantUML 的本地渲染），而非依赖外部服务的路径
3. wiki 的 maturity 字段不是装饰，是知识可信度的信任链记录——与 SecureClaw 定期巡检类似，应定期将 draft 文章升级为 reviewed
