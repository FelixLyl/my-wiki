# 可视化是理解工具的完整性检验

## 核心观察

将三个看似独立的工具并置，可以发现一条隐藏的逻辑链：[[代码仓库分析器]] 分析代码架构，输出含 Mermaid 图的报告；[[Markdown查看器技能]] 提供多引擎渲染，将 Mermaid 图变成可视化图表；[[Claude-Code源码架构]] 描述了 Claude Code 五层架构的设计决策。

这三者的交汇点是：**可视化输出是理解工具"理解深度"的可检验代理**。

## 理解工具的隐性假设

代码仓库分析器的设计哲学是"Why > What"——它强调理解设计决策，而非列出功能清单。但"理解"是内部状态，无法直接观测。Mermaid 架构图是这个内部理解的可验证外化：一张设计合理的图意味着分析工具真正理解了模块边界和依赖关系，而不只是堆砌文字。

Claude Code 源码架构本身也印证了这一点：其五层架构在逻辑上高度清晰，但一旦用图表示（AI核心 → 工具与Agent → 安全配置 → 终端UI → 记忆知识的五层依赖），依赖方向和边界立刻变得显而易见，而这些在纯文字叙述中可能被掩盖。

## 可视化作为完整性检验

这里有一个可操作的推论：**若一个分析工具的输出无法被可视化工具合理渲染，则该分析大概率存在结构性不完整**。

具体而言：
- 若 repo-analyzer 产出的 Mermaid 图在 markdown-viewer 中渲染失败（节点缺失、边方向混乱），说明源码分析阶段对模块关系的提炼出了偏差
- 若 Claude Code 五层架构图中某层与其他所有层都没有边，说明这层要么是错误抽象，要么被遗漏了关键连接

可视化由此从"最后一步美化"升格为"理解质量的回归测试"。

## 延伸：工具链的可验证环路

当分析、渲染、架构三类工具形成闭环时：
1. repo-analyzer 分析代码库 → 输出含 Mermaid 图的报告
2. markdown-viewer 渲染 Mermaid 图 → 产出可目视检验的架构图
3. 人或 Agent 对照架构图与实际代码 → 反馈分析的完整性

这个环路是 [[知识管理/做梦机制]] 中"自维护"思想在"理解工具"层面的具体实例：工具的输出不仅服务于用户，也暴露出工具自身的局限。

## 设计建议

对任何以"理解/分析"为目标的 Agent 工具，一个可复用的验收标准是：**要求工具在输出文字洞见的同时，输出至少一张结构图；若结构图有明显缺陷，优先修正分析逻辑，而非修正图的样式。**
