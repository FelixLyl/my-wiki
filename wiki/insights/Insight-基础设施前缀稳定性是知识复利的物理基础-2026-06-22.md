# 基础设施前缀稳定性是知识复利的物理基础

Prompt Caching 的核心机制是：**请求前缀完全不变，才能命中缓存**。任何一个字节的扰动都会使 KV Cache 失效，系统回退到从头预填充。这个在 LLM 工程中看似只是成本优化的细节，实际上揭示了一个更普遍的定律。

## 三条看似无关的线索

**线索一**：Coolify 的价值命题是"无供应商锁定"。其深层含义不只是价格，而是**配置的归属权**——应用配置存在自己的服务器上，基础设施的行为不会因第三方决策而悄然漂移。

**线索二**：Andrej Karpathy 的个人知识库理念建立在一个前提之上："I rarely touch the wiki directly. It's the domain of the LLM." 他信任 LLM 作为知识维护者，前提是 LLM 每次写入时面对的是**稳定的上下文结构**，而非随机变动的基底。

**线索三**：Prompt Caching 要求系统提示完全固定——"任何细微改动（包括空格、换行）都会导致缓存失效"。静态内容前置、动态内容后置，这不是 API 的偏好，而是 KV Cache 的物理约束。

## 碰撞点：稳定性是积累的前提条件

三条线索指向同一个结构：**积累需要稳定的基础层**。

Prompt Caching 告诉我们：知识注入（系统提示）必须是不变量，变量只能追加在后面。这与 Karpathy 的 wiki 架构完全同构——wiki 是稳定的知识前缀，对话历史是追加的动态层。

Coolify 在基础设施层做的事与此相同：将服务器状态、配置、证书稳定在自己控制的环境中，让每次部署的"前缀"不变，避免云平台的不可预期变更污染积累路径。

三者的共同结构是：

```
[稳定基础层] + [增量追加层] → 有效积累
[频繁变动的基础] + [任何追加层] → 复利清零
```

## 推论：缓存命中率是知识系统健康度的代理指标

一个实际的推论：如果你的 wiki 注入到 LLM 后缓存命中率很低，可能不是 API 的问题，而是知识结构在频繁重组。知识库前缀的稳定性，和 Prompt Caching 的命中率，指向同一个底层健康指标——**你的知识是否真正在沉淀，还是在原地重新排列**。

同理，如果 Coolify 管理的服务频繁需要重新配置，通常意味着底层设计不稳定，而不只是运维问题。

## 实践含义

- 写入 wiki 时，先问：这是在**稳固前缀**（扩展已有的稳定结构），还是在**污染基础层**（重写已有定义）？
- 设计 CLAUDE.md 时，静态规范写前面（缓存前缀），动态项目配置写后面（差量）
- 选择基础设施时，优先选择"行为可预期、不会主动漂移"的平台（Coolify 的价值在此）

知识复利不是努力的问题，是结构稳定性的问题。前缀不变，积累才能发生。
