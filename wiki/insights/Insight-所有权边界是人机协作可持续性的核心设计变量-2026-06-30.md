# 所有权边界是人机协作可持续性的核心设计变量

GStack、LLM知识库三层架构、OpenSpec 是三个领域差异极大的工具——一个管工程 sprint 流程，一个管个人知识库，一个管需求工件化。但它们解决的深层问题高度一致：**当人与 AI 长期协作时，如何防止系统在迭代中失控**。

三者给出的答案，都不是"更好的 Prompt"或"更强的 AI"，而是同一种结构设计：**在系统中显式划定每个区域的所有权和可变性规则**。

## 三种实践中的共同结构

**LLM知识库三层架构**把知识资产按可变性分层：
- `raw/` — 人类拥有，LLM 只读，永不修改（防止幻觉污染来源）
- `wiki/` — LLM 拥有，人类读取，可自由写入
- Schema 层 — 人类与 LLM 共同演化，约束行为规范

**OpenSpec** 把需求工件分区管理：
- `specs/` — 系统事实来源，人类与 AI 共同维护但需显式变更
- `changes/` — 每次变更的独立工件目录，AI 不得越权修改其他变更
- 聊天历史 — 明确排除在可信信息之外（"需求不能只活在聊天历史里"）

**GStack** 把工程流程按角色边界切分：
- 每个 slash command（`/office-hours`、`/plan-eng-review`、`/qa`）各管一段，不越权
- 人工决策点（"/autoplan 只上浮需要品味决策的节点"）显式嵌入流程
- 多 Agent 并行时，每个 Agent 知道自己在哪个阶段、该停在哪里等待

## 可变性控制的两类失效模式

缺乏所有权边界的协作系统通常以两种方式退化：

**模式一：AI 写坏了人类的东西**。LLM 修改了 raw/ 中的原始素材，污染了真相来源；OpenSpec 的 AI 直接改了 specs/ 而不走变更流程，规范悄悄漂移；GStack 的 Agent 绕过了 `/review` 环节直接 ship，没有人工复核。

**模式二：人类以为 AI 记住了某些约定，其实没有**。需求只在聊天历史里，下次会话 AI 全忘了；wiki 里没有 Schema 约束，AI 每次写法不同，积累的文章格式混乱；Agent 没有明确的阶段边界，上一个 Agent 的输出没有成为下一个的真正输入。

两种模式的共同根源：**可变性是隐式的，依赖信任而非结构**。

## 设计原则的提炼

这三个实践共同指向一个通用设计原则：**在持久性协作系统中，每个信息区域在设计阶段就需要显式指定三件事**：
1. 谁拥有这个区域（人类 / AI / 共同）
2. 这个区域的可变性规则（不可变 / AI 可写 / 需走变更流程）
3. 这个区域失效时的影响边界（仅局部 / 影响全局可信度）

这不是技术问题，而是治理问题。工具越强大，治理结构越需要前置设计——否则能力越大，失控速度越快。

## 一个尚未被充分重视的推论

当前大多数 AI 工具的设计默认"用完即走"：每次会话独立，AI 不对系统状态负责。但随着 Agent 越来越长期地运行在用户的系统中（代码库、知识库、工作流），**AI 实际上在积累"写权限"**——它可以修改文件、调用接口、生成下游输入。

这意味着所有权边界的设计不再只是工程优雅性的问题，而是**长期 Agent 系统可审计性的前提条件**。不能审计 = 不能修正 = 不能信任。
