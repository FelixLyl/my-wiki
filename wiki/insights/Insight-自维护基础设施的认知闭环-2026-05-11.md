# 自维护基础设施的认知闭环

**来源文章：** [[Andrej-Karpathy]] × [[Coolify]] × [[自学习复盘模式]]

---

## 三个领域的同构问题

Karpathy 说的问题是：谁来维护知识库？答案是 LLM，而不是人。

Coolify 解决的问题是：谁来维护基础设施？答案是自己的服务器，而不是第三方云平台。

自学习复盘模式解决的问题是：谁来修复 Agent 的错误？答案是 Agent 自己，而不是人工介入。

三个领域，同一个结构：**把维护责任从外部依赖转移回系统本身**。

---

## 共同的认知模型：维护权内化

传统的依赖关系是线性的：

```
产物（知识库/服务器/技能）← 外部维护者（人/云厂商/人工纠正）
```

Karpathy 模式、Coolify、自学习复盘模式都在做同一件事：把这个箭头折成一个环：

```
产物 ←→ 系统自身维护能力
```

这不只是效率优化，而是一种根本性的架构哲学转变：**可持续的系统必须内化自己的维护能力**。

---

## 维护权内化的三个条件

对比三个案例，维护权内化成功的前提有三个：

**1. 状态可观测**
- Karpathy 的 wiki：LLM 能读取所有文章，知道知识库的当前状态
- Coolify：通过 SSH 可以直接观察服务器状态，无黑箱
- 自学习复盘：Agent 能读取自己的执行日志，能看到错误发生了什么

如果维护者看不到被维护对象的真实状态，就无法完成维护。Karpathy 对 RAG 的批评正在于此：RAG 每次从头检索，永远不知道"知识库当前的积累状态是什么"。

**2. 写权限受控**
- Karpathy wiki：LLM 维护 wiki，但 raw/ 下的原始素材人工控制，不可被改写
- Coolify："停用 Coolify 后资源仍能继续运行"——平台有写权限，但不能锁住数据
- 自学习复盘：self-evolving-skill 能修改代码，但需要配合安全扫描，防止错误修复引入漏洞

写权限的受控程度决定了系统在出错时的可恢复性。

**3. 更新是增量的，不是覆盖式的**
- Karpathy wiki：新素材只添加到现有知识，不清空重来
- Coolify：新部署不覆盖旧配置，git push 触发增量更新
- 自学习复盘：知识卡片是"仅追加、永不修改"策略（[[Insight-错误记忆的缓存友好编码-2026-04-09]]）

增量积累是这三者能产生复利效果的根本原因。

---

## 一个尚未被充分挖掘的组合

如果把三者的核心能力叠加：

- Coolify 的**基础设施自托管**（数据主权）
- Karpathy 的 **wiki LLM 维护**（知识主权）
- 自学习复盘的 **Agent 自修复**（行为主权）

会得到一个在技术栈所有层面都具备自维护能力的系统。这个组合目前没有现成实现，但逻辑上是完整的：你的服务器自己管，你的知识 LLM 帮你管，你的 Agent 技能自己修复。

Karpathy 说"LLM 是 wiki 的维护者"——更完整的表述是：**可持续的 AI 原生系统，在基础设施、知识、行为三个层面都需要内化维护能力，并且三者的维护循环必须能互相反哺**。

---

## 潜在矛盾

这个架构有一个内在张力：**维护权内化依赖状态可观测，但状态可观测需要足够的系统开放度，而开放度会带来安全风险**。

Coolify 用"数据不经过第三方"来解决这个矛盾，Karpathy wiki 用"raw 不可改写"来解决，自学习复盘用"安全扫描"来解决。

三个解法的共同模式是：**开放写权限给系统自身，但设置一个不可绕过的外部审核层**。

这是"自维护"和"失控"之间的边界。
