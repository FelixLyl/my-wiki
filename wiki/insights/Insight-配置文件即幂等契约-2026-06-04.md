# 配置文件即幂等契约

## 碰撞来源

本文由三篇表面无关的文章碰撞产生：

- **[[幂等防重模式]]**：知识编译系统通过 LEDGER 账本确保同一素材不被重复处理，"增量永远优于全量"。
- **[[Codex-全能助手]]**：Codex 的记忆层（Memory）跨会话积累个人偏好和历史修正，减少每次会话重新描述的成本。
- **[[CLAUDE-md配置方法论]]**：CLAUDE.md 是向 AI 声明项目工作协议的配置文件，其核心价值在于精准度而非信息量，"每一行都应该是 Claude 自己推断不出来、但又影响输出质量的规则"。

## 洞见

这三篇文章在工程层面描述的是同一个问题的三种解法：**如何让一个智能系统在多次运行之间保持行为的一致性和可预测性？**

幂等防重模式用 LEDGER 解决的是数据层面的重复处理问题；Codex Memory 用持久化偏好解决的是交互层面的重复描述问题；CLAUDE.md 解决的是行为层面的重复配置问题。三者形成了一个"幂等三角"：

| 层次 | 问题 | 解法 | 载体 |
|------|------|------|------|
| 数据层 | 素材被重复入库 | Hash 防重 + LEDGER | compiled_ledger.json |
| 交互层 | 每次会话重新描述偏好 | 跨会话记忆持久化 | Memory 模块 |
| 行为层 | AI 每次推断出不同工作规范 | 声明式行为契约 | CLAUDE.md |

**核心命题：配置文件本质上是人写给 AI 的幂等契约。**

一份 CLAUDE.md 的作用，与一条数据库唯一约束等价——它不是描述"理想状态"，而是约束"每次运行都不能逾越的边界"。这也解释了为什么把 CLAUDE.md 塞满信息反而有害：过多的约束相当于给幂等检查增加了无意义的哈希字段，降低了匹配精度。

## 延伸推论

1. **配置文件的熵增倾向**：LEDGER 账本会随使用增长但不会缩减；CLAUDE.md 在团队实践中也有"越写越长"的倾向。两者都需要定期修剪，确保每一项约束都在主动工作，而非只是历史遗留。

2. **幂等性与 Agent 可靠性正相关**：Codex 的 Automation 功能（跨天、跨周自动唤醒执行长期任务）依赖的正是行为幂等性——如果每次重新启动都推断出不同的执行策略，自动化将无法信任。配置文件的精准度直接决定了 Agent 作为长期协作者的可用性上限。

3. **"最小配置原则"是幂等思维的延伸**：幂等防重系统只记录"路径 + mtime"两个关键字段；CLAUDE.md 最佳实践建议控制在 200 行以内。两者都体现了同一个工程直觉：最小化状态集合，才能最大化行为的可预测性。

## 开放问题

- 是否可以为 CLAUDE.md 引入类似 LEDGER 的"规则效用追踪"，记录每条规则被实际触发的频率，定期清除从未生效的规则？
- Codex Memory 的持久化记忆与 CLAUDE.md 的显式声明之间存在优先级冲突时，系统应如何裁决？这个问题在 Agent 系统设计中尚无标准答案。
