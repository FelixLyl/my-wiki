# 配置精简与记忆复利的悖论

## 碰撞来源

三篇看似属于不同维度的文章：

- **记忆不是功能，而是复利的基础**：AI 系统的真实竞争力在于记忆能否跨会话积累；功能层壁垒极低，记忆层才是难以复制的护城河；
- **CLAUDE.md 配置方法论**：精简、具体、可操作是 CLAUDE.md 的三个关键词，2000 行的配置会让 Claude 在上下文里迷失，生成质量反而下降；
- **Codex 全能助手（2026 更新）**：AI 编程工具完成感知→执行→记忆三层演进闭环，Memory 功能记住偏好、历史修正，目的是"减少每次会话重新描述的成本"。

## 洞见

**Codex 和 CLAUDE.md 的"记忆"正在做同一件事，但当两者并存时，CLAUDE.md 应该更短，而不是更长。**

初学者的直觉是：工具的记忆能力越强，就要写进去越多信息。Codex 记住了你的偏好，CLAUDE.md 塞满了你的偏好——两份"记忆"同时注入，context 里充斥着重复或矛盾的声明，AI 反而不知道该信哪个。

这正是 @vincemask 观察到的反模式：把项目历史、技术决策、个人偏好全部塞进 CLAUDE.md，结果 Claude 在 2000 行的上下文里迷失。这个反模式的产生，恰恰是因为开发者在"工具没有记忆"的旧假设下写配置，却在工具已经有了持久化记忆能力的新环境中使用这份配置。

**"记忆复利论"提供了正确的设计框架：** 不是把所有信息注入配置文件，而是把"哪些信息应该存在哪一层"想清楚。

| 信息类型 | 正确的存储层 | 错误的做法 |
|---------|------------|----------|
| 个人偏好、修正历史 | Agent 的 Memory（Codex/Claude 持久化层） | 写进 CLAUDE.md |
| 项目工程规范、协作模式 | CLAUDE.md（声明层） | 口头每次重复说 |
| 跨项目的知识积累 | Personal wiki / brain-loop | 分散在各项目 CLAUDE.md |
| 一次性上下文 | 对话消息本身 | 固化进配置 |

## 推论

Codex 的记忆功能与 CLAUDE.md 的精简原则不是互补关系，而是**替代关系的一部分**。随着 AI 工具的 Memory 层逐渐成熟，CLAUDE.md 的职责会进一步收窄——最终只剩下"该项目独有的、AI 无法从历史中自行归纳的约束"。

这是 Karpathy 准则"Simplicity First"在配置层面的必然延伸：不是人写得越少越好，而是每一行写在配置里的内容都应该是 AI 的 Memory 层无法自动积累的。

**复利的来源不是信息的堆积，而是信息存对了地方**——这是三篇文章交叉指向的唯一结论。

## 行动意义

维护 CLAUDE.md 的人应该定期做"信息分层审计"：
1. 这条规则，AI 的 Memory 功能还没有自动学到吗？
2. 这条规则，是这个项目独有的，还是所有项目都适用？
3. 这条规则，删掉之后 AI 的行为会变差吗？

通过这三问，每次审计都应该让 CLAUDE.md 变得更短，而不是更长。
