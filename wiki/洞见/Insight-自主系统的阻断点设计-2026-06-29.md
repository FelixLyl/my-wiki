# 自主系统的阻断点设计

自主系统的可信度不来自端到端判断能力，而来自在正确位置设置阻断点。

## 三个来源的碰撞

[[Karpathy-LLM编码准则]] 观察到 LLM 的结构性缺陷：它们会在不确定时静默假设、过度复杂化、产生正交编辑。他的应对策略不是"让模型更聪明"，而是给每步操作附加可验证的成功标准，把命令式指令转化为可循环校验的目标。

[[OpenClaw-Agent安全体系]] 的核心结论与此高度同构：高危操作前强制触发人工审批，"将'人工审批'插入 Agent 的危险操作路径，而非寄希望于 Agent 自身判断"。这两个系统对同一问题给出了相同答案：不信任连续执行，信任断点校验。

[[n8n]] 将这个问题从原则层落到了结构层。可视化工作流让"在哪里插入校验节点"变成了可设计的问题。一个 n8n 流程图可以直观地展示：哪些节点是自动流转，哪些节点前需要人工确认，哪些路径要先通过 Webhook 回调后才能继续。审批不再是事后约定，而是流程拓扑的一部分。

## 核心命题

**阻断点是自主系统架构的显式元素，而非边界外的补丁。**

传统软件的安全逻辑是：系统正常运行，异常时触发警报。自主 Agent 的安全逻辑必须反转：假设 Agent 会在错误路径上持续前进，因此要在设计阶段就标注出"此处必须停下"的位置，将人类判断编织进自动化链路，而不是等到出错再介入。

这个设计原则可以推广到三个层次：

- **语义层**（Karpathy）：任务语义不清时，Agent 主动停止并陈述歧义，而非猜测继续
- **权限层**（安全体系）：高危操作触发二次确认，不依赖 Agent 自我克制
- **拓扑层**（n8n）：工作流节点显式标记人工审批节点，审批路径与自动路径在图结构上分离

## 推论

一个成熟的 Agent 系统应能回答：你的阻断点在哪里？谁设计的？会不会被绕过？

如果阻断点全部依赖 Agent 的内生判断（"我认为这很危险所以我没做"），则系统的可信度上限等于模型能力的下限——这是脆弱的。如果阻断点是结构性的（权限要求、审批节点、验证钩子），则可信度独立于模型能力，成为系统的固有属性。

这与 [[可信Agent的根基是制度]] 形成共鸣：制度优于自律，结构优于判断。
